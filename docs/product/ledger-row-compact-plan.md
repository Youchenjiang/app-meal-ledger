# 明細列緊湊化計畫（Phase 2）

狀態：**已實作**（明細列固定一行,三圖示動作;本文件保留為決策紀錄）。

---

## 1. 目標

- 明細頁（現 `/ledger`）每筆紀錄**不得超過兩行**，最終收斂為**固定一行（已定案）**。
- 顯示**所有紀錄**：官方確認紀錄為主，草稿待審、掃描來源另外分區（沿用目前 Review queue 分法）。
- 每列高度固定；空狀態保留。

## 2. 單列內容（已定案）

- 一行內容：**MM/DD 日期（獨立窄欄）+ 標題（有品項時顯示品項、否則商家/來源）+ 商家小字（標題為品項時的第二行）+ 帳戶 · 類別（次要文字）+ 金額（右）**，狀態徽章緊貼；長內容 ellipsis 截斷。日期獨立成窄欄是為了不讓完整日期吃光 meta 空間，確保帳戶與類別這兩維度可見。標題以**購買的項目**優先（產品需求「Expense item/name is separate from merchant」），商家在標題下方仍可見。**軌道優先序**：`meta` 的 fr（1.15）大於標題（1），且狀態徽章**獨立成一個 track**——徽章原本與 meta 共用軌道、又吃掉 41px，導致帳戶·類別在 470px 以下被截成 `Da…`。**窄容器 fallback**：`@container ledger-rows (max-width: 404px)`，查詢錨在 `.ledger-kind-section`（`container: ledger-rows / inline-size`），所以判準是**列自己的容器寬度**而不是視窗寬度——窄面板與窄手機行為一致，不支援 container query 的引擎才退回 `@supports not (container-type: inline-size)` 內的 440px media query。觸發時 meta 換到自己的第二列（`"date name amount actions" / "date meta status actions"`），換取完整可讀的帳戶·類別（列高 56px，仍在 e2e 的 100px 上限內）。
- 動作只留**圖示**，同一行兩個：修改（鉛筆）、刪除（垃圾桶）。
- 「⋯」溢位選單已移除：情境動作（復發控制：暫停/恢復/取消週期，僅復發型紀錄；補齊資料，僅缺漏支出）收進浮動編輯視窗的 footer，編輯與刪除因此集中在同一介面。
- **刪除行為由設定決定（已定案）**：預設**作廢**（保留歷史、不計入餘額/報表），可在設定改為**真正刪除**（紀錄直接移除）——開關本身在[設定分區計畫](settings-restructure-plan.md)落地（行為規格見 [settings spec](../specs/settings/requirements.md)），本階段負責明細列的刪除動作依設定執行。

## 3. 已實作：篩選、排序與類型分區（Phase 2b）

在列高收斂的基礎上，明細頁（`/ledger`）追加「Search is a core ledger feature」的核心能力：

- **類型分區**：已確認記錄依類型家族分區塊渲染——`支出`（expense、refund、unresolved-expense）、`收入`（income、fund-addition）、`轉帳`（transfer）、`調整`（adjustment）。每區塊顯示筆數與**分幣別小計**（作廢記錄不計入小計）。
- **帳戶快篩（chips）**：水平捲動的帳戶 chips（「全部」+各帳戶），單點切換、再點一次取消——比下拉更快，回應「帳戶篩選更簡潔快速」。
- **類別／商家篩選（popover）**：各含搜尋輸入與筆數，點選即篩，再點取消；「清除篩選」一次重置全部條件。
- **快速搜尋**：輸入即時比對商家、類別、帳戶、備註與品項名稱。
- **排序**：日期（新→舊／舊→新）、金額（高→低／低→高）、商家（A→Z／Z→A）、類別（A→Z／Z→A）；排序只在區塊內生效。
- **空狀態**：篩選後無結果時顯示「沒有符合篩選條件的記錄」。
- **編輯表單可設週期**：`RecordEditor` 增加「下一個週期」區塊（記錄行為＋下期金額可能變動），讓既有一筆記錄也能轉為週期性；選「下期詢問我／下期自動記錄」即啟動週期（⋯ 選單出現暫停／取消），改回「僅本期」則關閉。純金額編輯不會誤動暫停狀態。週期只適用支出／收入／轉帳（與新增流程一致），V1 無頻率欄位（下期預設為月週期，自動記錄限固定金額）。
- **編輯改為浮動視窗**：`RecordEditor` 與 `UnresolvedExpenseEditor`（補齊資料）不再原地取代明細列，改由 `EditorDialog` 浮層呈現——列表不往下擠、背景鎖捲動，Esc／✕／點背景關閉。
- **刪除確認視窗化**：垃圾桶圖示改開 `ConfirmActionDialog`（作廢/真正刪除的訊息＋確認/取消），取代原本擠在列旁的內嵌確認框。
- **編輯視窗依內容撐高、永不內部捲動**：`record-editor-fields` 不再有 `overflow-y: auto`（先前短視窗下會出現框內捲動條，已徹底移除）。**解法是排版不是壓縮**——欄位改兩欄並排（金額滿寬、類別|商家、品項|原因、備註滿寬），週期區塊也兩欄（記錄行為|下期金額可能變動），輸入框維持舒適的 36px；713px 視窗下收合摘要 542px、展開設定 543px（展開不再多一張卡片，兩態幾乎同高），都有大餘裕。對話框 `margin: auto` 置中；即使極短視窗下溢出一點，overlay 的捲動條也隱藏（`scrollbar-width: none`）且 html 一併鎖定，畫面上永遠看不到捲動條，footer 仍可達。
- **版面自審修正（品項滿寬／下拉樣式／checkbox 對齊）**：① 原因欄隱藏時（非調整類型且無匯入/語音資料），品項名稱改 `full-span`，不再孤伶伶卡在左欄、右側空一塊（原因顯示時維持品項|原因並排）；② `.record-editor input, textarea` 樣式規則補上 `select`——先前「記錄行為」下拉掉回瀏覽器預設（17px 高、無 padding，幾乎點不到），現在與其他輸入框同尺寸（39px）；③ 「記錄行為」label 改跨兩欄置頂，select 與「下期金額可能變動」checkbox 共用同一行（baseline 對齊），不再有 label+select 堆疊撐高右欄、「僅本期」時 select 自動 full-span 不留空欄。
- **週期控制回歸表單**：週期按鈕（暫停／恢復／取消週期）不再放 footer，改收進「下一個週期」區塊——已設週期記錄顯示緊湊摘要（「下期自動記錄 · 固定金額」＋暫停／取消／修改設定），點「修改設定」才展開完整記錄行為控制；非週期記錄只留一行「設為週期」入口，展開後可收合。補齊資料（缺漏支出）同樣回到表單內。footer 只保留儲存／取消。
- **週期摘要顯示具體排程**：依業界慣例（金額＋下次日期＋頻率），摘要從抽象標籤改為具體排程——主行「每月 09/15」（V1 預設月週期，下次日期＝記錄日期＋1 個月，月底退回最後一天，依 accounting-rules.md）、次行「下期自動記錄 · TWD 480」（變動金額則顯示「金額可能變動」）；暫停中的記錄顯示「已暫停」徽章。
- **展開態週期設定修正**：① 點「設為週期」展開時預設「下期詢問我」（而非「僅本期」），動作與意圖一致；② 「僅本期」時隱藏無意義的「下期金額可能變動」checkbox 與排程預覽，改顯示「此記錄只記錄本期，不會重複。」；③ 選「下期詢問我／下期自動記錄」時，具體排程併入區塊標題行（「下一個週期 · 每月 09/15」），展開態不再重複顯示排程卡片——行為已在下拉、金額在金額欄，卡片只是把下拉的選項重講一遍（資訊重複）；「收合週期設定」加 ▲ 箭頭、靜止色改亮一階、hover 底線，明顯可點。新增表單（手動輸入）套用相同規則。
- **編輯視窗其他修正**：金額欄標題旁顯示幣別徽章（與明細列「TWD 480」一致）；modal 內 textarea 關閉 resize 把手；checkbox 修正（不再被 `.record-editor input` 樣式砸成滿寬方框）。
- **「原因」欄位只對調整顯示**：手動新增流程本來就只有調整類型有「調整原因」（必填 textarea），編輯器卻對所有類型顯示自由的「原因」欄位，與「備註」重複。已改為：僅調整顯示（標籤「調整原因」）；非調整類型只有在紀錄已有 reason 資料（匯入／語音帶入）時才顯示，避免隱藏既有資料；一般支出編輯器只留「備註」。
- **新增表單版面修正（CSS specificity bug + 欄位配對 + 填表順序）**：① 修復 `.draft-form fieldset`（0-2-0 權重）覆蓋 `.entry-details`（0-1-0）和 `.recurrence-control`（0-1-0）的 `border: 0; padding: 0` 的 specificity bug——兩者都被套上不必要的邊框和 14px padding，加了 `.draft-form .entry-details` 與 `.draft-form .recurrence-control` 規則（0-2-0 權重）覆蓋回來；② 品項名稱在 entry-details 2-col grid 裡孤伶伶佔左半（右半空），改為 `full-span`（加 `.entry-item-name-field` class）；③ CSS order 讓帳戶（order: 3）出現在 entry-details（order: 2）之後——填表順序不自然，改為 order: 1（帳戶在明細之前）；④ entry-details 加 `margin-top: 4px` 視覺分隔帳戶與明細。驗證：453 單元、15 e2e、typecheck、build 全綠。

### 3.1 列高目標

單行緊湊列：`min-height: 26px` + 上下 3px padding，`draft-list` gap 收斂；相對舊兩行卡片列（約 78px/列）**約縮減一半**。字級提升到計畫下限（見 3.4）後實測：**單行 47px/列**（容器 ≥450px）。窄容器不再只是換行，而是依寬度分三級（見 3.4）；最窄的 262px（320px 手機實際留給明細區的寬度）為 91px/列，把金額移到自己一列，換取品項／商家 158px、帳戶·類別 109px 完整可讀。320px 無水平溢出（e2e 驗證，含「meta 未被 ellipsis 截斷」與三個級別的 grid track 斷言）。

### 3.2 敵意內容與極窄容器（回歸測試）

`tests/e2e/ledger-hostile-content.spec.ts` 用「使用者真的打得出來的最寬資料」重跑同一輪寬度掃描：21 字 CJK 帳戶名、36 字拉丁帳戶名、三種幣別（TWD / USD / JPY，含小數），加上超長商家與品項。斷言按「長度是否有界」分三類：

- **有界**（日期、狀態徽章、金額）：任何寬度都不得被 ellipsis 截斷——這三個值一定放得下，被截就是缺陷。
- **無界**（品項、商家）：可截斷，但至少保留 **3 個字**。
- **帳戶 · 類別**：可截斷，但至少保留 **5 個字**——這是這一列存在的理由，不能縮成 `Da…`。

三個下限**都按字元數算、再用該欄位實際渲染的字級換算**（`fontSizeOf`）。寫死像素會在字級一改時悄悄變成更少的字：舊的 40px 在 13px 是 3 個字，在 16px 只剩 2.4 個，而測試仍會綠。

**支援下限＝容器內容寬 240px**（320px 手機留給明細區的寬度）；220/200px 仍測「較弱的契約」：有界值完整、列不超出版面，也就是退化時是「讓帳戶·類別少拿寬度」而不是「丟掉一個欄位」。

本輪實測並修掉三個缺陷：

1. **分區摘要不能換行（多幣別受害最重）**：`.ledger-section-heading > span` 原本 `white-space: nowrap` + ellipsis，於是 ① 同區多幣別時整種幣別的小計被省略號吃掉；② 它的 min-content 變成分區唯一 grid column 的 min-content，把**每一列**一起推出卡片外（實測：240px 卡片裡列寬 268px，三幣別時 361px）。改為換行——只在分隔符斷行、貨幣代碼與金額不分離——換行後摘要靠右。
2. **金額欄拒絕小數（`<input type="number" step="1">`）**：瀏覽器原生驗證會以 `stepMismatch` 擋下所有帶小數的金額，而原生驗證發生在 submit **之前**，所以表單根本沒送出、畫面也沒有任何訊息——`USD 98,765.43` 存不進去，TWD/JPY 因零小數而看不出來。改為 `step="any"`（精度仍由 app 自己的 `currencyPrecision` 把關）；`createExpenseRow` 現在斷言列數必須增加，這類「靜默沒存到」會讓測試直接紅。
3. **同一張卡裡兩種金額寫法**：列直接印 `record.amount` 原始字串（`TWD 1234567`），而正上方的小計走 `Intl.NumberFormat` 有千分位（`小計 TWD 1,234,887`）——同一個數字、同一張卡、兩種慣例，而列才是使用者真正在讀數字的地方。現在兩者都呼叫 `src/manualLedger/money.ts` 的 `formatAmount`（`formatAccountBalance` 改為轉呼叫它，列則經 `formatAmountString` 先解析記錄的十進位字串，讀不出來時退回原字串而非 `NaN`）。

驗證：兩個 layout spec 共 7 tests 在本機 Chromium 實跑全綠（含既有 3 顆像素快照）；`tsc -b`、460 單元測試、`test:docs` 全綠。上述缺陷另用「注入舊 CSS／舊 step／把列金額改回無千分位」的臨時 spec 反向驗證守衛真的會紅（該臨時 spec 跑完即刪）。

### 3.3 視覺階層（品項 > 金額 > 次要資訊）

列的**讓位順序**（標題先被截斷、帳戶·類別留到最後）已有斷言，但**誰最大聲**沒有；而這個關係一開始就是反的。品項是 `<strong>`，本身沒指定顏色，所以繼承 `.draft-card span`（那是一條為草稿清單寫的規則）的 `--text-muted`；金額則一路繼承到 `--text-primary`，成了整列最亮的字。幾何掃描看不到這件事——每個截斷斷言都通過，只有這一列最重要的關係是壞的。

修正只在 `src/styles.css` 兩條規則：`.record-item` 明確指定 `color: var(--text-primary)` 與 `font-weight: 700`；`.record-amount strong` 降到 `--text-secondary` + 600；日期／商家／帳戶·類別 維持 `--text-muted`。字重之所以明寫而不是倚賴 `<strong>` 預設的 `bolder`，是因為 `bolder` 會隨祖先字重往上跳，明寫才是契約。**不動字級、不動幾何**：三顆像素快照的畫框尺寸不變（346×107 / 466×90 / 926×90，重新錄製前後一致），只有文字像素改變。

守衛在 `ledger-layout.spec.ts`（`rowTextProminence`，位於 `layout-support.ts`），量的是讀者實際拿到的 WCAG 對比——背景取列自身最近的不透明祖先，而不是硬寫某個 token；深淺兩個主題都驗（app 預設深色，另備淺色）：

| 欄位 | 顏色（深 / 淺） | 對比（深 / 淺） |
|---|---|---|
| 品項 | `#e9e6df` / `#242321` | 12.70 : 1 / 15.45 : 1 |
| 金額 | `#c8c4bb` / `#4c4740` | 9.10 : 1 / 9.05 : 1 |
| 商家、帳戶·類別、日期 | `#9e9a91` / `#69645c` | 5.64 : 1 / 5.77 : 1 |

兩條下限防止「降級」被便宜行事：金額不得低於 4.5:1（降級不等於讓使用者看不清數字），且品項字重不得輕於金額（否則單靠顏色擋不住較粗的金額把目光搶回去）。反向驗證：注入修復前的顏色（品項 `--text-muted` / 金額 `--text-primary`）→ 品項 5.64:1、金額 12.70:1，守衛確實會紅。

驗證：兩個 layout spec 共 9 tests、整套 e2e 24 tests 在本機 Chromium 全綠；`tsc -b`、460 單元測試全綠。

### 3.4 字級下限與版面級別

依計畫 §5.2：**內文 16px、輔助資訊 14px**。列的欄位歸屬如下（皆在 `src/styles.css` 的 `.ledger-record-card` 規則內明寫，不倚賴繼承）：

| 類別 | 欄位 | 字級 |
|---|---|---|
| 內文 | 品項、金額 | 16px |
| 輔助 | 日期、商家、帳戶·類別、狀態徽章、作廢標籤 | 14px |

**字級不是外觀調整，它會移動幾何**，所以版面級別跟著重推。邊界是量出來的，不是選的：16/14px 下單行需要約 **450px** 容器才能讓**短**帳戶名（`Daily wallet · 日用`，113px）完整放進 meta 欄——掃描在 440px 與 420px 都失敗（meta 只有 109px、98px）；而 320px 手機只留給明細區 **262px**，兩列版在該寬度只給帳戶·類別 45–50px，也就是這份計畫要消滅的 `Da…`。

| 級別 | 容器寬（content box） | tracks | 列高 | 窄端實測（品項 / 帳戶·類別，敵意資料） |
|---|---|---|---|---|
| 單行 | ≥450px | 6 | 47px | 79 / 91px @450 |
| 兩列（meta 移到名稱下） | 300–449px | 4 | 70px | 85 / 85px @300 |
| 三列（金額自己一列） | ≤299px | 3 | 91px | 195 / 109px @299 |

三列級別的取捨是**用列高換可讀性**，且只在寬度真的付不起時才採：262px 下品項與帳戶·類別各得 158px／109px，遠高於 48px／70px 的下限。列高上限仍維持 100px（最窄級別 91px），「不超過四行文字」也在 e2e 斷言裡。

**級別邊界必須與 CSS、測試三處同步**：`@container ledger-rows (max-width: 449px)`／`(max-width: 299px)`、spec 的 `ONE_LINE_MIN_CONTAINER = 450`／`TWO_LINE_MIN_CONTAINER = 300`，而 `CONTAINER_WIDTHS` 同時包含兩個邊界與各自減 1 的寬度，所以「差一 px 就換版面」是被斷言的行為，不是巧合。

反向驗證：注入舊字級（13/11/10px）→ 16px／14px 下限的斷言會紅；另外舊的寫死像素下限（3×13＝39px）在新字級下只覆蓋 2.4 個字（3×16＝48px），這正是下限改成「按字元換算」的理由。

## 4. 中長期（未實作）
